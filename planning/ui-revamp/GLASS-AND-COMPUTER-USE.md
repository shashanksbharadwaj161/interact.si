# Owner clarification: computer-use companion, glass and edge light

16 October 2026. Supplements HITODAMA-DEEP-STUDY.md and supersedes opaque-panel defaults in earlier visual briefs. Preserve the original cyberpunk identity and Claude-primary direction. The owner wants the experience of a future desktop environment, with a full AI companion, rather than a dashboard as the main product. This is a Windows companion layer, not a claim that we are replacing the Windows kernel or shell.

## Priority: useful computer interaction

The core loop is invoke → deliberately speak/type or select context → understand → propose/perform a supported authorized operation → verify the actual result → report in place. Keep the current application in focus where possible. A tool result, a permission toggle, a prompt preview and successful execution are different things; surface their real state.

The island, contextual answer surface and optional expanded workspace share one session and appearance. Files, browser context, routines, memory, research, writing and account connections should extend that loop. The full workspace remains available for extended work and configuration. Do not add another large feature inventory before the basic native loop works.

## Material direction: glass, depth and luminous edges

- Floating dark smoked glass, actual translucency where supported, controlled background blur, restrained refractive highlights, fine luminous edges and layered depth. The desktop behind the companion should remain perceptible. Keep the material consistent across the island, expanded surfaces, settings, dialogs and controls.
- A CSS backdrop blur only blurs content behind an element inside the renderer. It does not prove that the real Windows desktop behind an Electron window is blurred. Evaluate the installed Electron/Windows native backdrop APIs and their OS support. Use real desktop material where possible, with an attractive solid fallback when unsupported, transparency is reduced or high contrast is active. Do not promise identical native blur on every Windows 10/11 build.
- Give text, inputs and dense content enough local opacity to remain readable on both bright and busy wallpapers. The entire app is not one unreadable transparent sheet. Keep body text crisp; avoid bloom on labels.
- Use original edge-light motion inspired by the behavior the owner describes on Samsung phones, not copied Samsung assets or exact visual effects. Add a controlled perimeter light around the island/expanded window and local edge highlights on interactive controls.
- Give light a semantic purpose: hover/focus highlights an available action; pressing produces a short local response; a real running task can send a restrained perimeter pulse; completion settles into a brief trace; a real alert can use amber. Every state has text/icon equivalents. No fake continuous activity, relentless flashing, moving hit targets or rainbow borders around every component.
- Keep animation continuous as the island expands into conversation, context or tools. Avoid overlapping multiple animated borders/shaders on the same element. Share motion/material tokens rather than a different effect per screen.
- Make edge lighting and transparency user-adjustable, with intensity, still/reduced-motion and off options. Honor Windows accessibility preferences. Pause effects while hidden, minimize animation cost and measure GPU/frame consistency on the actual laptop. Do not infer performance from screenshots.

## Why the previous result missed

The implementation sequence prioritized feature breadth and route completion, then visual styling. Source evidence shows the primary computer-use loop was incomplete: standard large window, context controls that attach no captured screen items, and text-only provider requests without a complete tool execution loop. Giving that structure neon colors and an orb did not create an ambient companion. Automated route/test coverage did not validate discoverability or successful daily use. The product needs focused interaction validation and coherent art direction, not more simultaneous feature fragments.

Hitodama's public demos are more compelling because they present a recognizable presence, contextual voice interaction and visible outcomes while another app remains in use. This is a judgment of public demonstrations, not proof its installed application works flawlessly or that every advertised feature is implemented.

## Prototype and acceptance

Apply these materials and edge-light states to the isolated companion experience prototype already assigned. Prioritize resting island → expanded command → context/action/result → collapse, plus customization. Clearly mark simulated listening/action states as design previews. Show over at least a light, dark and busy original mock desktop. Keep the native implementation separate and verify actual translucency, keyboard/focus, mixed-DPI displays, cancellation, real cloud/tool behavior and hidden GPU cost before claiming it works. Preserve API-key vault, selected-context disclosure, scoped IPC and trusted native action approval.
